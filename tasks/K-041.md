# K-041 — Dopasuj typy requestu API do JSON Schema

Cel: API v1 ma odrzucać typy JSON inne niż kontrakt, zamiast po cichu zamieniać tekst lub booleany na liczby.

Zakres: `apps/api/main.py`, testy `apps/api/tests/test_api_contract.py` oraz `contracts/openapi.yaml`, jeśli zmiana walidacji wymaga doprecyzowania kontraktu. Nie zmieniaj scoringu ani danych.

## Kroki

1. Dopasuj walidację `SearchRequest` do `contracts/search-request.schema.json` bez konwersji stringów lub booleanów na wartości numeryczne.
2. Dodaj przypadki dla `weight: "1"`, `weight: true`, `top_k: "2"` i niecałkowitego `top_k`; zachowaj poprawne requesty z typami liczbowymi.
3. Jawnie sprawdź i udokumentuj zgodność zachowania integralnych JSON liczb dziesiętnych z Draft 2020-12, zamiast przypadkowo odrzucić lub zaokrąglić wartość.

## Kryteria odbioru

- [ ] String i boolean nie są akceptowane jako `weight` ani `top_k`; błąd ma status 422 i zgodny `ErrorResponse`.
- [ ] Poprawne dodatnie wagi oraz integer `top_k` nadal działają; niefinitywne, niecałkowite i poza zakresem wartości są odrzucane.
- [ ] Test porównuje zachowanie requestu z JSON Schema i potwierdza brak cichego coercion.
- [ ] Pełny zestaw testów i kontrola planu przechodzą.

## Sprawdzenie

`uv run --locked --dev python -m pytest -q`, walidacja przypadków requestu przez `contracts/search-request.schema.json`, `python tools/check_planning.py`, `git diff --check`.

## Powód dodania / wpływ

W `apps/api/main.py` pola Pydantic mają domyślną lax walidację: lokalnie potwierdzono `weight: "1"` → `1.0` oraz `top_k: "2"` → `2`, mimo że kontrakt wymaga number i integer. Prawidłowe requesty K-007 działają, więc poprawka nie blokuje integracji; ścisłość zmniejsza ryzyko, że błędne dane UI przejdą jako poprawna konfiguracja.
