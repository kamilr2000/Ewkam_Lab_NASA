# E-014 — Napraw widok mobilny E-002

Cel: Użytkownik może przeczytać i obsłużyć cały statyczny przepływ E-002 na wąskim ekranie bez poziomego ucinania kontrolek, mapy, etykiet i kart wyników.

Zakres: głównie `apps/web/src/styles.css`, w razie potrzeby `apps/web/src/App.tsx`, na opublikowanym PR #5 `ewelina/E-002-information-flow`. Projektowe kryteria telefonu opisuje `design/analysis-flow.md`. Nie dodawaj API, obliczeń ani danych.

## Kroki

1. Popraw układ telefonu dla szerokości 320, 375 i 390 CSS px; trzymaj kryteria i selektory w kolejności oraz układzie zgodnym z dokumentacją telefonu.
2. Sprawdź, czy mapowe etykiety, skala, treść pustego stanu, karty wyników i stopka mieszczą się w obszarze widoku.
3. Upewnij się, że widoki tablet/desktop przy breakpointach 780/781 i 1150/1151 px nadal zachowują czytelną hierarchię.
4. Uruchom build, sprawdź szerokość dokumentu wobec viewportu i opublikuj dowody w PR/handoffie.

## Kryteria odbioru

- [x] Przy 320, 375 i 390 CSS px `document.documentElement.scrollWidth <= document.documentElement.clientWidth`; żaden selektor, tekst, element mapy ani karta nie jest ucięta, także przy klasycznym pasku przewijania.
- [x] Na telefonie kryteria nie są zestawione obok siebie w sposób skracający nazwy lub jednostki; zachowano kolejność z `design/analysis-flow.md`.
- [x] Szerokości 780/781 i 1150/1151 px zachowują czytelny układ bez nachodzenia treści.
- [x] `npm run build --prefix apps/web` przechodzi, a zrzuty sprawdzonych szerokości i ograniczenia są opublikowane.
- [x] UI nadal jasno pokazuje, że jest szkieletem bez aktywnego API, pomiarów i rankingu.

## Sprawdzenie

`npm run build --prefix apps/web`; dla każdego wskazanego viewportu sprawdź `document.documentElement.scrollWidth <= document.documentElement.clientWidth`, zaznaczenie fokusu i widoczność treści. Zachowaj zrzuty 320, 375, 390, 780, 781, 1150 i 1151 px jako dowód przeglądu.
