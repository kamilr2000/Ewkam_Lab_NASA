# E-021 — Popraw kontrast i czytelność bazowego UI

Cel: użytkownik może odczytać drobne etykiety i objaśnienia statycznego ekranu także przy słabszym widzeniu; bazowe style spełniają minimalny kontrast WCAG AA bez utraty układu telefonu.

Zakres: `apps/web/src/styles.css` oraz raport w `handoffs/E-021-ui-readability.md`. Nie zmieniaj przepływu API, treści naukowych ani obliczeń.

## Kroki

1. Zmierz pary kolorów tekstu i tła faktycznie używane przez statyczny ekran; zapisz wartości przed poprawką.
2. Podnieś kontrast poniżej 4.5:1 dla zwykłego tekstu i popraw najdrobniejsze objaśnienia oraz podpisy, zachowując hierarchię wizualną.
3. Zbuduj aktualny production preview i zapisz `innerWidth`, `clientWidth`, `scrollWidth` oraz `body.scrollWidth` dla faktycznie raportowanych 320/375/390/780/782/1150/1151 CSS px. Punkty 780/782 obejmują obie strony breakpointu `max-width: 780px`; nie nazywaj 782 pomiarem 781 px.
4. Na aktualnym renderze sprawdź ucięcia i nakładanie przy tych szerokościach oraz widoczny fokus klawiatury przy 320 px. Dołącz świeże zrzuty lub równoważny, odtwarzalny dowód; nie przedstawiaj pomiarów ze starszego snapshotu jako bieżących.
5. Uruchom testy web i produkcyjny build, zapisz wyniki oraz ograniczenia. Nie wymuszaj klasycznego scrollbara bez potrzeby; jego brak odnotuj jako ograniczenie.

## Kryteria odbioru

- [x] Zwykły tekst ma kontrast co najmniej 4.5:1 z rzeczywistym tłem; wyjątki dla tekstu dużego lub nieaktywnego UI są jawnie oznaczone i uzasadnione. Po integracji mapy ponownie obliczono dodatkowe pary MapLibre na złożonych tłach CSS; minimum wynosi 6.82:1.
- [x] Drobne etykiety, jednostki i objaśnienia są łatwiejsze do odczytania; deklaracje tekstowe w aktualnym CSS mają co najmniej 9 px, a kontrast brandingu nie został zmieniony.
- [ ] Przy siedmiu szerokościach aktualnego preview zapisano `innerWidth`, `clientWidth`, `scrollWidth` i `body.scrollWidth`; nie ma poziomego overflow, uciętego tekstu ani nachodzących etykiet.
- [ ] Fokus klawiatury jest widoczny przy 320 px, a handoff zawiera świeże zrzuty lub równoważny, odtwarzalny dowód aktualnego renderu.
- [x] Testy web (40/40) i `npm run build --prefix apps/web` przechodzą; handoff podaje pary kolorów, kontrast przed/po, dotychczasowe pomiary i ograniczenia.

## Sprawdzenie

Oblicz kontrast z luminancji sRGB dla użytych par foreground/background. Zbuduj produkcyjny frontend i obejrzyj aktualny render przy 320, 375, 390, 780, 782, 1150 i 1151 CSS px. Zapisz `innerWidth`, `clientWidth`, `scrollWidth` oraz `body.scrollWidth`; potwierdź brak overflow, przycięć/nachodzenia i widoczny fokus klawiatury przy 320 px. Raportuj wyłącznie faktyczne wymiary.

## Powód dodania / wpływ

Ręczny pomiar istniejącego `apps/web/src/styles.css` wykazał poniżej 4.5:1 m.in. stopkę (#687771 na #11191a: 3.79:1), drobny tekst pomocniczy panelu (#6d7d78 na #172122: 3.80:1), podpisy narzędzi (#71807c na #11191a: 4.31:1) oraz jednostki (#778782 na #172122: 4.36:1). Są to zwykłe teksty mniejsze niż duży tekst, więc utrudniają odczyt wymaganych stanów i ograniczeń produktu. WCAG 2.2 SC 1.4.3 podaje próg 4.5:1 dla zwykłego tekstu; [źródło W3C](https://www.w3.org/TR/2023/REC-WCAG22-20231005/). To ograniczona poprawka bazowego ekranu i nie zastępuje pełnego audytu interaktywnego UX w E-008.
